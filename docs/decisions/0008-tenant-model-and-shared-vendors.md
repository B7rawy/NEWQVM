# ADR-0008: نموذج الـ Tenant الكامل + الموردون ككيان عالمي قابل للمشاركة

**الحالة:** مقبول — 2026-07-22 (بناءً على متطلب صاحب المشروع)

## القرار

### 1. الـ Tenant = Workspace كامل
المنصّة **SaaS متعدد المستأجرين بالكامل**. الـ `tenant` = مؤسسة وسيطة (مثل Qparts) تملك
**عالماً كاملاً معزولاً**:

```
tenant (workspace)  ← ساب-دومين خاص + هوية + إعدادات + باقة
├── workshops (الورش العميلة) + فروعها
├── vendors (الموردون المرتبطون بهذا الـ workspace)
├── users (موظفو المشغّل + مستخدمو الورش + مستخدمو الموردين)
├── RFQs → quotations → orders → deliveries → returns → invoices
└── portals: بوابة الورشة + بوابة المورد + لوحة المشغّل
```

العزل مضمون بالـ RLS على `tenant_id` (ADR-0003). لا يوجد أي تسريب بين workspaces.

### 2. الموردون: كيان عالمي + جدول ربط (الأهم)
**المورد لا يملكه tenant واحد.** التصميم:

| الجدول | المحتوى | الـ tenancy |
|---|---|---|
| `vendors` | هوية المورد العالمية: الاسم القانوني، السجل التجاري، الرقم الضريبي، بيانات التواصل الأساسية | **بلا `tenant_id`** (عالمي) |
| `vendor_branches` | فروع المورد | تابعة لـ `vendors` |
| `tenant_vendors` | **جدول الربط**: أي مورد مفعّل في أي workspace + الإعدادات الخاصة بالعلاقة (الحالة، شروط الدفع، التصنيف، هامش/اتفاق، تاريخ الارتباط) | **`tenant_id` + RLS هنا** |
| `vendor_users` | مستخدمو بوابة المورد | مرتبطون بالمورد، وصولهم مقيّد بالـ tenants المرتبط بها |

**السلوك اليوم:** كل workspace يرى ويدير مورديه فقط — العزل عبر RLS على `tenant_vendors`،
وكل استعلامات الموردين تمرّ من خلاله. المورد المُنشأ داخل workspace يُربط به تلقائياً.

**السلوك مستقبلاً (بلا أي تغيير سكيما):** ربط نفس المورد بأكثر من workspace = صف إضافي في
`tenant_vendors`. كل workspace يحتفظ بشروطه وتسعيره وسجله الخاص مع نفس المورد، دون رؤية بيانات الآخر.

**قاعدة حرجة:** بيانات المعاملات (عروض الأسعار، أوامر الشراء، الفواتير، التقييمات) تحمل
`tenant_id` دائماً ولا تُشتق من `vendors` — حتى مع مورد مشترك، تاريخ كل workspace معزول تماماً.

## السياق
- القديم: single-tenant متنكّر — "الشركة" صف في `lists` والموردون جدول واحد مسطّح بلا أي مفهوم workspace.
- طلب صريح: workspaces منفصلة تماماً + استعداد لمشاركة الموردين لاحقاً.

## البدائل المرفوضة
- **`tenant_id` مباشرة على `vendors`:** أبسط اليوم، لكن مشاركة مورد لاحقاً تعني تكرار سجله
  (بيانات متضاربة، تقارير مكسورة) أو ميجريشن مؤلم على بيانات حيّة. مرفوض لأن المتطلب معروف مسبقاً.
- **نسخة من المورد لكل workspace:** ازدواج بيانات — نفس مرض النظام القديم.

## النتائج
- كل استعلام موردين يمرّ عبر `tenant_vendors` (لا يُستعلم `vendors` مباشرة من طبقة التطبيق).
- فهارس: `(tenant_id, vendor_id)` على الربط، و`(tenant_id, …)` على كل جداول المعاملات.
- بوابة المورد تحتاج اختيار الـ workspace عند ارتباطه بأكثر من واحد (يُعالج في المرحلة 4).
